## wslc-compose v0.2.1

Patch for wslc 3.0.3.0, where `wslc system session run` can exit 1 with `ERROR_INVALID_HANDLE` after a host-gateway script has already finished. v0.2.0 `down` frequently failed with exit 1 on wslc 3.0.3 (every cycle in our real test) because each `down` makes several session calls that intermittently fail. `up` with `host-gateway` plus a published port no longer rolls the project back.

### Install / upgrade (Windows PowerShell or PowerShell 7, no admin required)

```powershell
irm https://raw.githubusercontent.com/DawnMagnet/wslc-compose-go/main/scripts/install.ps1 | iex
```

Pin this version:

```powershell
& ([scriptblock]::Create((irm https://github.com/DawnMagnet/wslc-compose-go/releases/download/v0.2.1/install.ps1))) -Version v0.2.1
```

Then open a new terminal:

```powershell
wslc-compose version     # main command, works in every shell
wslc compose version     # PowerShell sugar, forwards to wslc-compose
```

### Changes

- **Session scripts survive `ERROR_INVALID_HANDLE`** ([#12](https://github.com/DawnMagnet/wslc-compose-go/pull/12)).
  Each host-gateway script installs an `EXIT` trap that writes `<nonce>-<attempt> <exit>` to
  `/run/<owner>.status` (a temp file, then `mv -f`). When wslc returns `ERROR_INVALID_HANDLE`, the client
  reads that file and uses only this attempt's line. The full script runs again only when the line is missing,
  so an earlier success cannot hide a later failure. The outer loop is up to 5 attempts with a 2s backoff. On each
  `ERROR_INVALID_HANDLE` the status file gets its own up to 5 reads, also with a 2s backoff (not a shared
  budget). Persistent errors fail after about 8s. The theoretical worst case is about 48s of waiting, excluding
  wslc execution time and flock waits (up to 10s each).
  `TERM`, `INT` and `HUP` exit 143, 130 and 129 first, so a signal is recorded as itself and not as success.
  `ERROR_SHARING_VIOLATION` and `ERROR_ALREADY_EXISTS` are still retried, as in v0.2.0, without treating them as
  a finished script. Every session call, including the status read, is given an empty stdin, and session stdout
  is captured. On a non-zero script exit, wslc's stderr is kept. Failures writing or renaming the status file
  are ignored and do not change the exit code.
- **`down` and `up` on wslc 3.0.3.** A recorded exit 0 is success, so the intermittent `ERROR_INVALID_HANDLE`
  that made v0.2.0 `down` fail no longer fails the command when the script recorded exit 0. `up` with
  `host-gateway` plus published ports no longer rolls the project back after the chains are installed. An empty
  `down` of a project that uses host-gateway still runs one idempotent cleanup, same as v0.2.0. A project that
  does not use host-gateway, and has neither the label nor the marker, makes no session call.
- **Write-ahead host-gateway marker.** Before the install script runs, `up` writes a `host-gateway` file in the
  project state directory. Rollback keeps that file, so a failed `up` is still cleaned on the next `down`.
  On wslc 3.0.3, `down` runs the idempotent cleanup whenever the compose file uses host-gateway, a container
  carries `com.wslc.compose.host-gateway=v1`, or the marker is set. That is also what removes chains left by
  v0.2.0, which did not write a marker. **Behavior change:** failing to write the marker now fails `up`.
  The first revision of this fix only warned, and it wrote the marker after the script had already run.

### Upgrade notes

- On wslc 3.0.1, v0.2.1 emits exactly the same commands as v0.2.0; the only new 3.0.1 behavior is the
  leftover-marker warning.
- On wslc 3.0.1 or an unknown version, a leftover marker makes `down` warn and keep the marker. Run `down`
  again after upgrading to wslc 3.0.3 so the leftover rules can be removed.
- After upgrading from v0.2.0, run `down` once on wslc 3.0.3 for any project that used host-gateway. Cleanup
  runs when the file still uses host-gateway, a container still has the label, or the marker is present.

### Verified

Environment: Windows, wslc 3.0.3.0.

- Multiple networks and aliases, static IPv4, `ip_range`, secrets (file and environment), configs,
  `extra_hosts` and `host-gateway` (including DNAT to a published port), and idempotent `up`.
- Repeated `up` / `down` of a service with `host-gateway` and a published port exits 0.
- `localhost` and `host.docker.internal` are reachable.
- The WCG iptables chains are empty after `down`.
- An `up` that fails on a port conflict rolls back and leaves no chains.

### Not verified

- Busybox ash signal behavior. Unit tests check the `EXIT` trap on bash and dash, and on busybox ash when that
  binary is installed. The ash inside the wslc session VM was not part of the Windows run. A `TERM` received
  while waiting on `flock` may take up to 10s before exiting with 143.
- iptables idempotency beyond the cases above. The Windows run covered repeated `up`/`down` and the
  port-conflict rollback. Installing over chains that already exist, cleanup when those chains are already
  gone, and more than one project at once were not checked on that machine.
- Same as v0.2.0, still unverified: real IPv6 subnet behavior, Windows file sharing conflicts, junctions.

### Assets

Same layout as v0.2.0: UPX-packed `windows-amd64` / `linux-amd64` binaries, uncompressed arm64 binaries,
`install.ps1`, the `wslc compose` wrappers and `checksums.txt` (SHA-256 of every asset).
